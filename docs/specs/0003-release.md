# 0003 — Release automation and Homebrew distribution

Status: proposed. Approved when its pull request merges into `spec/mir-282`.
Epic: [MIR-282](https://multica.ai/miran248/issues/MIR-282).
integration: `spec/mir-282`. This spec builds on
[spec 0002](0002-container-harness.md) and
[ADR 0002](../adr/0002-container-harness.md), which are merged into
`spec/mir-270` and are not yet on `main`: they define the scope, box, harness
container and image-pin vocabulary, and this spec does not restate it.

## Problem

`msbx` has no tag, no release and no install path that does not need a Rust
toolchain. The documented install is `cargo install --path .`; the harness image
pin and the container cutover's rollback each need a named binary version, and
`multica-workspace` has no version at all, so the catalog cannot be pinned. A
Homebrew tap is the macOS install and upgrade path once a second machine or a
second person appears.

## Outcome

Two repositories, one release chain, no hand tags. release-please owns the
version, the changelog, the `vX.Y.Z` tag and the GitHub release in both
repositories; the sandbox's release is created as a draft for cargo-dist to
fill. cargo-dist builds the macOS arm64 and Intel artifacts from that tag,
uploads them to the draft, undrafts it and publishes `Formula/msbx.rb` to
`miran248/homebrew-tap`. The formula installs both `msbx` and `msbx-run` from
the prebuilt archives, so a fresh Mac installs and upgrades without a Rust
toolchain.

```
commit on main
  → release-please PR (version, CHANGELOG, manifest)
  → human merge
  → release-please creates tag vX.Y.Z + draft release
  → tag push with a PAT/App token → cargo-dist workflow
  → macOS arm64 + Intel archives and checksums
  → upload to the draft, undraft
  → Formula/msbx.rb pushed to miran248/homebrew-tap
  → brew install miran248/tap/msbx
```

The first release is `v0.1.0`. The container cutover of
[spec 0002](0002-container-harness.md) is released through this same pipeline,
never hand-tagged. A release's rollback pair is the previous tag plus its image
digest.

## Non-goals

- Linux and Windows artifacts. Linux waits for a Linux host; Windows has no
  consumer.
- Signing, notarization, a core `homebrew-core` formula, a cask, a Docker image
  or a crates.io publish.
- A release cadence, maintenance branches, backports or a prerelease channel.
- Homebrew bottles and source-build formulae: the formula consumes the prebuilt
  archives.
- An npm publish of `multica-workspace`; its version exists to pin the catalog.
- Any automatic update inside `msbx`; Homebrew performs the upgrade.
- Choosing PAT versus GitHub App: both are accepted; the human supplies one.
- Changing the scope, box or harness-container contract of
  [spec 0002](0002-container-harness.md).

## Vocabulary

Release-only terms; the sandbox vocabulary stays with
[spec 0002](0002-container-harness.md).

- **Release PR** — the pull request release-please opens on `main` with the next
  version, the changelog entry and the updated manifest. Merging it is the
  release act.
- **Draft handshake** — release-please creates the tag and a draft GitHub
  release; cargo-dist uploads the artifacts to that draft and undrafts it.
- **Tap** — `miran248/homebrew-tap`, the repository Homebrew reads formulae
  from. `brew install miran248/tap/msbx` is the install.
- **Formula** — `Formula/msbx.rb`, generated by cargo-dist on every release and
  overwritten, never hand-edited. It installs both binaries.
- **Release token** — the PAT or GitHub App token that makes the tag a real
  event. It is provisioning, not a design choice.
- **Release child** — the final-stage ticket that merges the integration branch
  into `main` and cuts the release.

## release-please

release-please is the only version owner in both repositories. Both already use
Conventional Commits.

**`miran248/multica-sandbox`** uses `release-type: rust`: it bumps the version
in `Cargo.toml` and `Cargo.lock`, writes `CHANGELOG.md` and records the released
version in `.release-please-manifest.json`.

**`miran248/multica-workspace`** uses `release-type: simple` with a new
`version.txt` at `0.1.0`: it bumps that file and writes `CHANGELOG.md`. The
simple strategy's default initial version is `1.0.0`, so the config sets
`initial-version: "0.1.0"` explicitly.

Both repositories set:

- `include-component-in-tag: false` and the default `v` prefix, so the tag is
  exactly `vX.Y.Z` and matches cargo-dist's trigger.
- `bump-minor-pre-major: true`: before `1.0.0`, a breaking change bumps the
  minor, never the major. A `feat` bumps the minor and a `fix` bumps the patch.
  `1.0.0` is a deliberate later decision, not a side effect of a commit.
- A release action on `main` only, with the release token below. It never runs
  on the integration branch.

The sandbox additionally sets `draft: true` and `force-tag-creation: true`:
GitHub does not create a git tag for a draft release until it is published, and
the tag must exist before cargo-dist can react to it. The workspace has no
artifacts, so it publishes its release directly and needs neither flag.

The sandbox's `.release-please-manifest.json` is committed **empty**. The rust
strategy's initial release version is `0.1.0`, and `Cargo.toml` already says
`0.1.0`, so the bootstrap does not introduce a second number. (The strategy's
initial value is hard-coded; it is not read from `Cargo.toml`, so the two must
agree at bootstrap.) Seeding the manifest with `0.1.0` would make release-please
treat it as the last release and turn the first `feat` into `0.2.0`. The empty
manifest is what makes the first release `v0.1.0`. No `bootstrap-sha` is set:
the first release PR's changelog covers the commits since the repository's
start, and the stage ticket records the PR it produces.

The workspace manifest is empty for the same reason, with `initial-version`
supplying `0.1.0`.

No other process writes a version, a changelog or a tag. `cargo release`,
`release-plz`, manual versions and manual tags are out.

## cargo-dist

cargo-dist is the only artifact builder. It is pinned in the repository
metadata, and the generated release workflow is committed and regenerated by
the pinned version when the configuration changes; it is not hand-edited.

The configuration:

- `targets` are `aarch64-apple-darwin` and `x86_64-apple-darwin` only.
- `installers = ["homebrew"]`, `tap = "miran248/homebrew-tap"`,
  `publish-jobs = ["homebrew"]`, `formula = "msbx"`.
- `create-release = false`: dist assumes a draft release for the current tag
  exists, uploads the artifacts to it and undrafts it when all uploads finish.
  It creates no release and no tag.
- The pinned version's default macOS runners are `macos-15` (arm64) and
  `macos-15-intel` (x86_64), which are the two settled targets. A
  `github-custom-runners` entry is added only if the pinned version's default
  differs; the stage ticket records the default it observed.
- `repository`, `homepage` and `description` must be in `Cargo.toml`; only
  `description` is there today. `repository` is the GitHub source host
  cargo-dist derives, so adding it is a pipeline acceptance criterion, not
  optional polish.

The generated workflow triggers on `push` of a tag matching
`**[0-9]+.[0-9]+.[0-9]+*`, which `v0.1.0` and every `vX.Y.Z` match. The exact
pattern of the pinned version is recorded in the stage ticket, not assumed
across versions.

`create-release = true` is rejected in [ADR 0003](../adr/0003-release.md).

## The draft handshake

1. A release PR is merged on `main`. release-please creates the tag ref for
   `vX.Y.Z` and a **draft** GitHub release with that tag, using the release
   token.
2. The tag push starts the cargo-dist workflow. (A tag created by
   `GITHUB_TOKEN` would not start it; that is why the release token is a PAT or
   an App token.)
3. cargo-dist builds both targets, uploads the archives, checksums and the
   formula artifact to the draft, and undrafts it. The release is published
   when the artifacts are all present.
4. The same run's homebrew publish job pushes `Formula/msbx.rb` to the tap.

The draft must exist before the upload step; release-please creates the tag ref
and the draft in the same run, and the build gives the release time to appear.
A failed upload is recovered by re-running the cargo-dist workflow for the same
tag, never by re-tagging. The pinned cargo-dist version's `host` step performs
the undraft when the last artifact is uploaded; the stage ticket records that
step and adds `gh release edit <tag> --draft=false` only if the pinned version
does not.

## Targets, archives and the formula

Each release has one archive per target plus checksums and the source tarball
cargo-dist produces by default. The formula selects the arm64 or Intel archive
by `Hardware::CPU`, verifies its `sha256`, and installs every executable in it
with `bin.install "msbx", "msbx-run"`.

- The formula fetches prebuilt binaries and has no source build, so a tap needs
  no bottle and `brew install` needs no Rust toolchain. cargo-dist does not
  generate a bottle.
- The formula is regenerated and overwritten on every release. Hand edits are
  lost at the next release and are not a rollback mechanism.
- Homebrew serves exactly one version of a formula. A downgrade is not
  `brew install`; see Rollback.
- The tap repository must exist before the first release. The human creates an
  empty, public `miran248/homebrew-tap`; Homebrew finds it by the `homebrew-`
  prefix and the install command elides it, and a public tap needs no GitHub
  authentication to install.
- The formula name is `msbx` for the package even though the archives also
  carry `msbx-run`.

## The release token

One token kind is provisioned by the human, in either form:

- a fine-grained PAT (or a classic PAT with `repo`) scoped to the three
  repositories, or
- a GitHub App installed on the three repositories, with a token minted in the
  workflow.

Required permissions:

| Repository | Permission |
| --- | --- |
| `miran248/multica-sandbox` | contents: write, pull requests: write |
| `miran248/multica-workspace` | contents: write, pull requests: write |
| `miran248/homebrew-tap` | contents: write |

The sandbox stores it as `RELEASE_TOKEN` for release-please and as
`HOMEBREW_TAP_TOKEN` for cargo-dist's formula push; the workspace stores it as
`RELEASE_TOKEN`. `GITHUB_TOKEN` is not sufficient for release-please: events it
creates do not start another workflow, so the tag would never reach
cargo-dist. This is the provisioning boundary; PAT versus App is the human's
choice and does not change the workflows. Rotating the token is revoking it and
updating the three secrets.

## Install, `init` and `brew upgrade`

The install path is `brew install miran248/tap/msbx`. The formula puts symlinks
to both binaries in `$(brew --prefix)/bin`. `cargo install --path .` remains the
path before the tap exists (or on a host without Homebrew); it installs both
binaries into `~/.cargo/bin`.

`msbx init` is the step after install, and it is idempotent. It installs the
`msbx.test` resolver and writes the DNS unit with the absolute path of the
binary that ran `init`. That recorded path is the upgrade risk:

- The Homebrew `bin` entry is a symlink into the versioned Cellar directory.
  Homebrew replaces that symlink on `brew upgrade`, but the Cellar path itself
  changes and the old one is removed.
- `msbx init` therefore must be run as `msbx` on `PATH`, so it records
  `$(brew --prefix)/bin/msbx` (the stable symlink), not the Cellar path.
  `current_exe` on macOS keeps the symlink rather than resolving it; the
  stage ticket verifies this on the installed formula.
- `brew upgrade` re-points the symlink, so the recorded unit path survives. If
  the unit was installed from a Cellar path, or the binary moved for any other
  reason, re-running `msbx init` rewrites the unit at the current path. The
  README and the formula's caveats say so.
- C1 records the unit's executable path, and `doctor` warns when that path is
  gone or `msbx dns` does not answer. A stale unit is a reported warning, not a
  silent failure.

The same rule covers `cargo install`: the binary lives at `~/.cargo/bin/msbx`
and `init` records that path; a `cargo install` upgrade keeps the path.

## First release and the cutover

- The sandbox's first release is `v0.1.0`, cut when the release child merges
  `spec/mir-282` into `main` and the human merges the `0.1.0` release PR.
- The workspace's first release is `v0.1.0` from its own release PR. It is the
  version the cutover names when it pins the catalog.
- The container cutover of [spec 0002](0002-container-harness.md) is released
  through this pipeline, never hand-tagged. The pipeline must therefore be on
  `main` before the cutover release is cut; that ordering is the release
  child's job, and the cutover keeps its own image-pin rollback material until
  the first green release on `main`.
- A release is identified by its tag. The binaries, the image pin and the
  catalog version named in a release ticket are that release's record.

## Rollback

- **Bad release.** Revert the offending commit on `main`; release-please opens
  the next patch or minor release PR; the human merges it; the new tag is the
  fix. Tags and published releases are never moved, deleted or re-created.
- **Install an older release.** Homebrew has only the latest formula. The
  previous release's archives stay on GitHub, so an older version is installed
  by hand from its archive (or `cargo install --git … --tag vX.Y.Z`), and
  `msbx init` is re-run if the binary path changed. A downgrade is manual; the
  tap is not a downgrade channel.
- **A broken formula.** Fix the generator or the release, cut the next patch,
  and let the tap be overwritten. The tap is never hand-edited as the fix.
- **The container cutover.** The rollback pair is the previous tag plus the
  image digest recorded for it, with the DSH archive kept per
  [spec 0002](0002-container-harness.md) until the first green release on
  `main`. Rolling back the harness is the cutover's procedure, not this spec's.
- **A yanked release.** Homebrew publishes one version and has no yank. A
  published tag is not withdrawn; the recovery is a patch release.

## Verification

Record, in the stage tickets, not assume:

- **release-please's first version.** Bootstrap the sandbox manifest empty,
  let the action open its first release PR, and record the proposed version
  (`0.1.0`) and the files it changes. Record that a seeded `0.1.0` manifest
  would propose the next version from commits instead. The action's first PR is
  the evidence, not the strategy's documentation alone.
- **The draft and the tag pattern.** Record the exact tag trigger in the
  generated workflow of the pinned cargo-dist version, and confirm
  `create-release = false` consumes a draft release for that tag and undrafts
  it. Run one tag end to end and record that no release or tag was created by
  cargo-dist. Record that `dist plan` resolves the GitHub source host from
  `[package].repository`, so the new metadata is present before the tag.
- **`brew upgrade` and the resolver unit.** Install `0.1.0` from the tap on
  macOS arm64 (and Intel where available), run `msbx init` from the `bin`
  symlink, record the unit's executable path, upgrade to the next release, and
  record that the unit still answers. Repeat once with `init` run from the
  Cellar path to record the stale-path warning and the re-init recovery.
- **The formula's contents.** Inspect the generated `Formula/msbx.rb` and
  record that `bin.install` covers both `msbx` and `msbx-run`, that the URLs
  and `sha256` select the arm64 and Intel archives, and that the formula has no
  source build and no bottle.
- **The tap and the token.** Record that `miran248/homebrew-tap` exists before
  the first release, that the three secret names are present, and that the
  release token, not `GITHUB_TOKEN`, created the tag. A release-please run that
  does not start cargo-dist is a failed check.
- **End to end.** On both macOS architectures, `brew install
  miran248/tap/msbx`, then `msbx init`, then `msbx doctor`; `msbx-run` starts a
  box for a real task. The existing `cargo fmt --check`, `cargo clippy -- -D
  warnings`, `cargo test` and CI checks stay green.

## Risks

- Homebrew's single-version rule makes the tap a roll-forward channel only;
  a downgrade is manual and a published tag is never moved.
- The release token is a single point of failure and a broad credential; it is
  kept out of every checkout, rotated by secret update, and never logged.
- macOS-only artifacts leave Linux users on `cargo install` until a Linux host
  and target exist.
- Release-please and cargo-dist are two independent actions with one handshake;
  a missing draft, a `GITHUB_TOKEN` tag or a token without pull-request write
  fails the chain after the tag exists. The recovery is re-running the
  cargo-dist workflow, never re-tagging.
- The generated workflow is version-coupled: changing the pinned cargo-dist
  version regenerates it, and a hand edit is overwritten.
- The workspace release and the sandbox release are independent tags in two
  repositories; the cutover pins both, and a name that is not a released tag is
  a finding.
- A formula with no bottle still downloads a per-architecture archive on every
  install; the cache and Homebrew's normal update path apply, but the first
  install needs network access to the GitHub release.
